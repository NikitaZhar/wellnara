# Боевая инструкция по работе с кодом

## 1. Главный принцип
Выполняй **только задачу пользователя**.  
Не расширяй задачу.  
Не добавляй новые цели.  
Не меняй формулировку задачи.

---

## 2. Алгоритм работы
1. Прочитать и понять существующий код.
2. Проверить код по всем требованиям (раздел 3).
3. Если код соответствует требованиям — **не менять**.
4. Если есть нарушения — исправить **минимально необходимым способом**.
5. Провести аудит предложенных изменений.
6. Если требуется новая функциональность — добавить **минимальный новый код**, не ломая существующий.
7. Минимизировать изменения: удалить лишний и мёртвый код, не ухудшая решение.
8. Провести аудит всего нового и изменённого кода.
9. Выполнить доступные тесты, сборку, проверку типов, линтер и статический анализ.
10. Если аудит или проверки обнаружили нарушение — исправить его и повторно проверить затронутую часть.
11. Выдать результат:
    - что было;
    - что стало;
    - почему изменение необходимо;
    - полный текст новых и изменённых файлов.

ИИ проверяет все применимые к затронутому коду пункты. Неприменимые пункты пропускает без добавления искусственных изменений.

---

## 3. Требования к коду (ядро)

ИИ проверяет все применимые к затронутому коду пункты. Неприменимые требования пропускаются и не являются основанием для изменения кода.

### 3.1 Clean Code
- Методы выполняют одну задачу и не содержат неоправданной сложности.
- Нет необъяснимых числовых и строковых значений, требующих именованной константы.
- Нет чрезмерной вложенности и запутанного потока управления.

### 3.2 SOLID
- S — одна ответственность.
- O — расширяемость без изменения стабильного кода.
- L — наследники не ломают контракт.
- I — интерфейсы не раздуты.
- D — зависимости через абстракции при нескольких реализациях.

### 3.3 Clean Architecture
- Контроллеры — вход/выход, без бизнес‑логики.
- Сервисы — бизнес‑логика.
- Репозитории — доступ к данным.
- DTO — только данные.
- Нет SQL в сервисах.
- Нет бизнес‑логики в репозиториях.
- Нет циклических зависимостей.

### 3.4 Cloud‑readiness
- Конфигурация извне.
- Нет секретов в коде/логах.
- Логирование структурированное.
- Таймауты на внешние вызовы.
- Повторные попытки ограничены.
- Операции идемпотентны.
- Нет локального состояния, мешающего масштабированию.

### 3.5 PostgreSQL
- Учитывать `NULL`.
- Уникальные ограничения.
- Внешние ключи.
- Нет частичных транзакций.
- Нет N+1 в затронутом коде.
- Нет deadlock‑опасных последовательностей.
- Нет race condition при записи.
- Запросы корректны и оптимальны.
- Миграции добавляются только тогда, когда они необходимы для запрошенного изменения схемы. Существующие применённые миграции не изменяются.

### 3.6 Spring
- Контроллеры без бизнес‑логики.
- Сервисы без SQL.
- Репозитории без бизнес‑логики.
- DTO не содержат бизнес-логики и доступа к инфраструктуре.
- @Transactional — только там, где нужно.
- Не менять маршруты/DTO/формат JSON/статус‑коды без запроса.

### 3.7 JavaDoc
Добавлять JavaDoc только если:
- пользователь запросил,
- или изменяется публичный элемент,
- или публичный элемент нарушает требования.
JavaDoc добавляется по запросу пользователя либо к новому или изменённому публичному элементу.

JavaDoc должен содержать:
- назначение;
- параметры;
- результат;
- исключения;
- граничные случаи;
- особенности транзакций/БД/HTTP.

### 3.8 Тестируемость
- Логика отделена от инфраструктуры.
- Бизнес‑код тестируем без БД.
- Тесты отражают реальное поведение.
- При изменении поведения — тесты обновляются.
Выполнить доступные тесты, сборку, проверку типов, линтер и статический анализ. Не утверждать, что проверка пройдена, если она не запускалась.

### 3.9 Безопасность
- Нет секретов в коде.
- Нет секретов в логах.
- Нет секретов в ответах API.
- Валидация входных данных.
- Нет SQL‑инъекций.

### 3.10 Минимизация
- Для реализации требуемой функциональности используется минимально необходимый объём кода.
- Изменения — только необходимые.
- Новый код — минимальный.
- Нет лишних абстракций.
- Нет лишних файлов.
- Нет лишних зависимостей.
- Нет оптимизаций без запроса.
- Нет рефакторинга ради рефакторинга.

---

## 4. Правило минимального вмешательства
Если код соответствует требованиям — **не менять**.  
Если нарушение есть — исправить **минимально возможным** способом.  
Если требуется новая функциональность — добавить **минимальный новый код**, не ломая существующий.

---

## 5. Аудит

После исправления существующего кода провести аудит всех внесённых изменений.
После реализации новой функциональности провести аудит всего нового и изменённого кода.
Проверить код по всем применимым требованиям раздела 3.
Если аудит обнаружил нарушение:
1. исправить его;
2. повторно проверить изменённую часть;
3. повторить затронутые инструментальные проверки.
Не завершать работу при наличии неисправленного подтверждённого нарушения.

---

## 6. Формат результата
Для каждого изменения указать:
- где изменено;
- что было;
- что стало;
- почему изменение необходимо.
После описания предоставить полный текст каждого нового и изменённого файла.
Не использовать Git patch.
